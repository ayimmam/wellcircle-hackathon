# Planning task: Well Circle points economy, provider tools, and social growth loops

Well Circle is a Telegram Mini App connecting wellness providers (gyms, spas, therapists, wellness practitioners) with users in Ethiopia, built as a three-service monorepo: FastAPI + SQLAlchemy + Supabase/Postgres backend (Vercel serverless), React 18 + Vite frontend (Vercel), and a python-telegram-bot worker (Railway, single replica). Users earn and spend a points currency; providers list products/services redeemable for points and run paid events/bookings. This is a produce-a-plan task, not an implementation task — deliver an architecture and rollout plan with concrete data-model and API changes, sequenced by effort and impact, not working code.

Do not guess at anything you cannot verify from the codebase or from the web research below. Where a decision genuinely depends on business context I haven't given you (pricing psychology, regional payment norms, moderation staffing, legal/regulatory constraints on loyalty-point systems in Ethiopia, etc.), stop and ask me directly rather than assuming a default.

## Current system state (verified, do not re-derive or contradict this)

**Points**: `User.points_balance` is a single integer column — there is no transaction/ledger table; history is reconstructed from `CommunityFeedEvent` rows. Earning is hardcoded in `backend/app/services/points_engine.py` (explicitly commented `"""Legacy Points engine"""`): +10 for a daily community check-in, +50 flat for any successful paid booking (`backend/app/crud/booking.py`), `challenge.reward_points` for completing a provider/admin-created community challenge, and peer-to-peer point gifting via post reactions (`backend/app/crud/post.py`) which transfers existing balance rather than minting new points. Tiers (seed/sprout/grove/forest) are computed by `get_points_tier()`, duplicated verbatim in both `points_engine.py` and `backend/app/crud/user.py`. Spending only happens one way: redeeming a `Product` whose `price_etb` field is actually a points cost despite its name (`backend/app/models/product.py`), creating a `UserRedemption` that providers/admins mark fulfilled. Daily decay (`backend/app/services/scheduler.py`, `decay_points_job`) removes 5 points/day after 3 days of check-in inactivity, run via APScheduler off-Vercel or cron on Render. There is no fixed points-to-ETB exchange rate anywhere; `Product.price_etb` (points) and `ProviderEvent.price_etb` (real ETB, paid via Telebirr/M-Pesa) share a field name but are unrelated currencies.

**Events**: `ProviderEvent` (`backend/app/models/provider_event.py`) is created only by providers, one at a time, with capacity/spots tracked via `EventInventoryLog`. There is no RSVP model — participation is inferred entirely from a paid `Booking` row. There is no attendance verification, check-in, or evidence/photo-proof mechanism anywhere in the codebase. Event cancellation has a "TODO: Refund logic (Phase 4)" — refunds are unimplemented.

**Provider dashboard** (`frontend/src/pages/ProviderDashboard.jsx`): four tabs — Analytics, Events, Products, Subscriptions. Providers can set product point-costs and event ETB prices, view live analytics, view (but not action beyond delivery-status) redemptions, and create challenges with a reward_points field. There is no customer list/CRM view and no "give points directly to a customer" action anywhere in the API or UI.

**Social/referral**: no referral or invite-a-friend system, and no contact-import feature exist at all. Two distinct group concepts coexist: `Circle` (user-created, portable, join-by-code, weekly-points leaderboard, `backend/app/models/circle.py`) and `Community` (provider-owned space tied to a wellness category where check-ins/bookings/challenges/feed happen, `backend/app/models/community.py`). Provider invite codes (`provider_invite.py`) exist only for onboarding new provider businesses onto the platform, unrelated to user referrals.

**Admin**: no endpoint anywhere lets an admin or provider directly adjust a user's `points_balance`. The only approval workflows in `backend/app/api/admin.py` are provider-application approve/reject and redemption delivery-status updates.

## Part A — Ground the plan in real provider/event data

Research actual wellness-provider categories, service structures, and event formats relevant to an Ethiopian (primarily Addis Ababa) urban wellness market — gyms, spas/salons, yoga/fitness studios, nutrition/therapy practitioners, wellness retreats/pop-up events. Look at how comparable regional or emerging-market wellness marketplaces structure provider profiles, service listings, and event/class scheduling. Use this to sanity-check and refine the provider/event data model changes proposed in Parts C and D below — e.g., are `ProviderEvent` fields (capacity, single active event per provider) realistic for how these businesses actually run recurring classes or pop-up sessions? Cite what you found and where it changes a recommendation.

## Part B — Redundancy and maintainability cleanup

Identify and produce a remediation plan for redundant/duplicated logic that harms performance or maintainability, prioritized by risk of touching it. Known candidates already confirmed in the codebase (verify and expand, don't just restate):
- `get_points_tier()` duplicated in `points_engine.py` and `crud/user.py` with no shared source of truth.
- `points_engine.py` self-described as a "Legacy" engine with hardcoded constants (`POINTS_CHECKIN`, `POINTS_DECAY_PER_DAY`, `DECAY_AFTER_DAYS`) — no config table or admin-tunable rates, which will directly block Part D's "responsible-personnel event points" and "provider-awarded points" features unless refactored first.
- `Product.price_etb` naming collision with `ProviderEvent.price_etb` — same field name, two incompatible currencies (points vs. real ETB), a correctness hazard for anyone touching pricing code.
- Absence of a points transaction ledger — history is reconstructed from `CommunityFeedEvent`, which will not scale once more point-earning event types are added (Parts D/E add at least three new ones) and makes auditing/reversal (needed for Part D's abuse handling) impractical as-is.
Also do a broader pass across `backend/app` and `frontend/src` for any other duplicated business logic, dead code, or N+1/polling inefficiencies worth flagging alongside these known ones — but do not invent problems that aren't there.

## Part C — Competitive research: point-based, trust-reliant wellness apps

Research comparable point/loyalty-based apps that depend on provider trust and community/social dynamics (fitness/wellness loyalty platforms, class-credit marketplaces, gym-network apps, habit/reward apps with a social layer). Identify which mechanics are genuinely high-impact relative to their build cost for a small team running on free/low-cost infrastructure (Vercel/Railway/Supabase free tiers, per `CLAUDE.md`) — flag per-feature whether it fits free tiers or needs a paid dependency, and let me decide on any that don't fit free tiers. Propose a prioritized shortlist (not an exhaustive feature dump) of features that would plausibly (a) increase user-side usability/engagement and (b) increase provider earnings or provider retention on the platform, explicitly tied back to gaps you find in the current system (e.g., no CRM view for providers, no ledger, no referral loop).

## Part D — Realistic point valuation and new earning mechanisms

Design a coherent points-valuation model given that no fixed points↔ETB exchange rate currently exists anywhere in the codebase:

1. **Provider-set point costs for free/complimentary services.** Providers currently set point costs for redeemable `Product` rows with no guidance. Design a recommendation mechanism that suggests a point cost to a provider when listing a free/complimentary service, based on what comparable providers (same category, similar market) charge in points for similar offerings — specify what "comparable" means (category match? geographic proximity? service duration/type?), where this computation runs, and how it's surfaced in `ProviderDashboard.jsx`'s product-creation flow.

2. **Evidence-based event participation points.** Design a flow where a designated "responsible personnel" role (clarify: is this a per-event volunteer, a fixed community role, or provider staff — recommend an option and justify it against the existing role model in `backend/app/models`) submits photo evidence of participation in an event to earn points. Photos are sent to the Telegram bot (not DM'd ad hoc to an individual) which enqueues them into a review queue surfaced in the admin dashboard for approve/reject — design the queue's data model (a new table, not reusing `CommunityFeedEvent`), the bot-side submission flow (what command/flow in `telegram-bot/`), the admin approve/reject UI and endpoint, and how approval mints points (via the ledger from Part B, not a bare balance increment).

3. **Provider-initiated point awards to existing customers.** Add a dashboard action (new tab or addition to the Products/Analytics tab in `ProviderDashboard.jsx`) letting a provider award points directly to a customer who used their service. Guardrail: only allow awarding to users with a verified prior interaction with that provider (an existing successful `Booking` or a `Community` membership/check-in tied to that provider — specify which you'd require and why), plus a rate/volume cap to blunt self-dealing — but keep the actual award action itself low-friction (one tap, no multi-step approval) since the verified-interaction requirement is meant to be the guardrail, not additional review steps. Specify the cap values you'd recommend (e.g., per-customer-per-week, per-provider-per-day) and how they'd be enforced (DB constraint vs. application check) and logged for later audit.

For all three, specify how they compose with the existing decay job (Part B's ledger refactor) and whether `last_checkin_at`-driven decay still makes sense once points can be earned through non-check-in paths, or whether decay eligibility needs to change to reference "any points-earning activity," not just check-ins.

## Part E — Social growth loops (Duolingo-style, adapted for a friend-group referral app)

Well Circle's `Circle` (user-created, join-by-code) concept is the natural home for friend-group dynamics but currently has no invite/growth mechanics beyond sharing a join code manually. Design, in priority order by expected impact-to-effort ratio:
- Contact-based invite flow (respecting Telegram Mini App constraints — Telegram Mini Apps cannot access a phone's native contacts API directly the way a native app can; research what Telegram's Bot API / Mini App SDK actually permits for invites/deep-linking, such as `switchInlineQuery` or bot-generated shareable deep links, and design around real platform capability rather than assuming native contact-list access).
- Social proof surfaces (e.g., "N friends in your circle checked in this week," leaderboard visibility, friend activity feed) grounded in the existing `Circle.weekly_points` leaderboard data that already exists — don't invent a new leaderboard system when one exists.
- Friend recommendation nudges tied to existing `Circle`/`Community` membership data.
Flag anywhere a proposed mechanic would require data Well Circle doesn't currently collect (e.g., phone numbers, contact permissions) and what the minimal viable data model addition would be.
